# Hosted Pix subscription rehearsal

The public game continues to use server-created Stripe Checkout Sessions for paid monthly Pix. A recurring Payment Link is a reusable public address, and Stripe accepts a checkout with its account-reference query parameter removed. That can start billing a person whose subscription the game cannot associate with an account. A static portal login verifies the customer's billing email, but the game cannot use it to cancel a subscription or query a missed event on the customer's behalf. These limits apply even if the storefront hides the purchase button. [Stripe Payment Link parameters](https://docs.stripe.com/payment-links/url-parameters) · [Hosted customer portal](https://docs.stripe.com/customer-management/activate-no-code-customer-portal)

## Exercise the fallback locally

Use a dedicated Stripe sandbox and a local D1 database with all migrations through 0007. Set `STRIPE_RECURRING_LINKS_SANDBOX=true`, `STRIPE_TAX_READY=true`, the sandbox webhook signing secret and a test-mode cancellation portal in `STRIPE_RECURRING_PORTAL_URL`. The game’s three Pix providers must be available. Expose this checkout only on localhost or a loopback address. A public hostname or live checkout URL cannot enable this path.

Configure `STRIPE_RECURRING_PAYMENT_LINKS` with all four Pix product IDs. Each entry has a distinct Stripe Payment Link ID, monthly price ID and test URL. For example, the entry for Pix Starter has the form `{"id":"plink_Example","price":"price_Example","url":"https://buy.stripe.com/test_Example"}`. Use the USD monthly amounts from the game catalog. Configure quantity one, card payments, automatic tax, and no trial, coupons, proration or optional line items. Configure Stripe's one-subscription limit and cancellation-only portal. Set the success redirect to the local game's `/?purchase=complete&session_id={CHECKOUT_SESSION_ID}`.

Forward signed sandbox events for checkout.session.completed, customer.subscription.created, customer.subscription.updated, customer.subscription.deleted, invoice.paid, invoice_payment.paid, charge.refunded and charge.dispute.created/updated/closed. Use a snapshot event destination compatible with Stripe's invoice-payment and invoice-parent fields. Thin events lack the information this rehearsal needs. Real charges, subscriptions or Payment Links are unnecessary for the automated tests. [Stripe InvoicePayment fields](https://docs.stripe.com/api/invoice-payment/object) · [Stripe event delivery](https://docs.stripe.com/webhooks#event-ordering)

## What makes a period eligible

1. The signed-in game account opens a test link with a short-lived checkout ticket and its prefilled billing email. A signed completion must match the issued ticket, link, billing email, price total, currency and tax result. A receipt URL or email alone grants no subscription.
2. The worker joins the bound subscription to its active status, a paid matching invoice for one monthly period, and a full matching card payment. It preserves these facts independently so signed events can arrive in any order. A refund, open or lost dispute, terminal cancellation or expired period removes access. A later paid period can restore access after a previous period was refunded.
3. The portal link opens Stripe's email-authenticated billing interface. Account deletion waits for cancellation to finish. A cancellation scheduled for the end of the period can be undone at Stripe, so scheduling alone does not complete that step.
4. A mismatched or missing ticket, altered price, unsupported billing option or missing webhook leaves the grant closed. Replaying a receipt from another game account cannot transfer it. Retain the signed checkout, invoice and payment references in the Stripe sandbox to investigate and resend a missing event.

The test suite exercises signed events and the real account/checkout/receipt endpoints against SQLite. Run `node --import tsx --test tests/hostedPix.test.ts tests/storeCommerce.test.ts`. This rehearsal does not create or activate Stripe links. A production release would additionally need an authenticated purchase entry point, customer-scoped billing management, and a way to reconcile missed provider events and finish account deletion. The existing API-backed integration provides that path.
